# JIT

x86-64 user code translated to AArch64 and run inside a Hypervisor.framework VM, as decided on 2026-11-19 (see [decisions.md](decisions.md) and [cpu.md](cpu.md#hypervisorframework)). The design follows 86slopper's (see its `docs/architecture.md`, "VM runtime layout"), simplified: there is no guest kernel, so no shadow paging of x86 page tables. Our own page tables mirror the regions in `crates/memory`.

Status (2026-11-20): stages A and B work, C and D are under way (see "Speed work, 2026-11-20" for the latest measurements), and the JIT is what `ps5slop run` uses by default (`--interpreter` turns it off). ScreenTester5 and DriftCheck run correctly under it, with 0 differences from the interpreter in verify mode over 30 to 40 s of each. Measured with release builds:

- ScreenTester5 draws its menu 0.2 s after start (2.5 s with the interpreter), and its RGB flash mode runs at 60 frames a second, the vblank rate (no frame at all in 5 s with the interpreter).
- DriftCheck flips about 30 frames a second (none in 6 s with the interpreter). Its frames take a little over 1/60 s, so this is its own work, not exits.
- Both now interpret only a few thousand instructions per second.
- Minecraft (2026-11-19, `PS5SLOP_JIT_STATS=1`, release build, headless, to its stop at `sceAgcCreateShader`): 214.4 M instructions translated and 33.6 K interpreted, 0.86 M lookup misses (0.57 M of them HLE calls, 0.25 M first translations of a block, 34 K blocks put back in the table after a collision) and 24 K untranslated exits, in about 2 s. Before the instructions below from `adc` on were translated it was 198.0 M translated, 17.5 M interpreted, 16.1 M lookup misses and 2.2 M untranslated exits in 27.9 s. Most of that was one `vmovntdq` loop in a `memset`: the loop's branch back to the untranslated instruction missed the lookup table on every iteration. After the second pass below (and with more AGC code, so it now stops later, at `libSceAgcDriver` NID `w2rJhmD+dsE`): 218.9 M translated, 13.6 K interpreted, 0.86 M lookup misses and 10 K untranslated exits in 1.8 s.
- Balatro (2026-11-19, same conditions, to its stop at `libSceAgc` NID `MWiElSNE8j8`): 417.5 M translated and 7.6 K interpreted, 0.57 M lookup misses and 2.8 K untranslated exits, in 1.3 s. Before the second pass it was 400.1 M translated, 14.8 M interpreted, 1.40 M lookup misses and 1.85 M untranslated exits in 7.7 s. Most of that was one `memcpy` loop in a loaded module (`prefetchnta` and `vmovntdqa`), then BMI2 `bzhi`/`pdep`/`pext`, `crc32`, `cld` with `repe cmpsb`/`cmpsd`, and `jp`.

## Speed work, 2026-11-20

Measured with release builds, headless, on this Mac (14 cores) with the GPU commands parsed and dropped (the base before vic's Metal renderer), `PS5SLOP_GPU_STATS=1`, flips per second over the last 20 s of a 42 to 45 s run. Other agents' ps5slop processes sometimes ran at the same time; each number below was taken when none was running at the start, and single runs vary by a few flips per second, so the before and after runs were made back to back. With the renderer on, flips are paced to the 60 Hz vblank, so 60 is the ceiling there.

| Step | Minecraft flips/s | Balatro flips/s |
| --- | --- | --- |
| Before (`xtsrnuqz`) | 8 to 11 (stuck before sign-in) | 64 to 108 (varies with load) |
| Lock-free VM entry and exit | 10.7 | 92 |
| Untranslatable code exits through the lookup table | 14.1 | |
| x87 translated | 10.5 (more work done per frame, same rate) | 119 |
| Thread natives, tables changed in place | 12.0 | 175 |
| Login event and NP stubs (past sign-in) | 33 to 40 | 133 (other load) |
| Coverage pass (packed FMA, narrow shifts, ...) | 46 to 73 | 195 |
| Lock-free native check, bigger lookup table, stage 2 | 53 to 59 | |
| Final, tier 2 off (three runs, 2026-11-20) | 55.9, 52.5, 52.7 | 196 (base build back to back: 62) |

What each step found and fixed, in order:

- **The machine lock.** `sample` showed the busy guest threads spending about 45% of their time waiting for the `Machine` mutex, which every VM entry and exit took twice, and 25% running guest code. Entry now checks the mirrored generation, the active table pool and the TLB epoch with atomics and takes the lock only when the tables must change; `load` copies YMM directly and sets only the registers that changed since `store` (it had built a `Vec` through a `flatten` iterator per entry).
- **Lookup misses at untranslatable code** (3.1 M in 40 s) each took the lock and decoded the instruction again. Such addresses now get a lookup entry pointing at a stub that exits straight to the interpreter (`INTERP_EXIT`).
- **x87.** 29 M of the 34 M interpreted instructions in 40 s of Minecraft were x87 (chosen from the opcode counts only: the hot ones are in Sony's `libc.prx`, which we do not disassemble). Translated instructions per 40 s went from 4.0 G to 10.2 G, interpreted from 34 M to 9.4 M. The frame rate did not move, which showed the frame was bounded elsewhere.
- **Guest mutex starvation and a spinning wait** (HLE, see [decisions.md](decisions.md)): the main thread was blocked about 60 ms at a time on per-object mutexes held by a worker (found by logging long `acquire` waits with the owner and the guest return addresses), and a thread spun in `pthread_cond_timedwait` because CLOCK_MONOTONIC deadlines were read as wall-clock times.
- **Page-table rebuilds.** Every direct-memory map, reserve and release (about 170 a second) rebuilt all TTBR0 tables from scratch, kicked every vCPU out and made each thread wait for the lock; four workers spent a third of their time there. Changes are now made to the live tables in place unless an address that stays mapped loses access (see "Memory changes" below): 5,212 full rebuilds per 30 s became about 1,500, then fewer than that per minute of steady state.
- **Thread natives.** `scePthreadGetspecific` and `scePthreadGetthreadid` were 14 M exits per 30 s. They, and `pthread_self`, now run inside the VM (`Native::Getspecific`, `ThreadId`, `SelfThread`). A native's lookup slot can be taken by a colliding block; the host now puts it back on the next miss (before, it fell back to the host function for good, which had also been happening to `memset` and `memcpy`).
- **Sign-in.** With the speed-ups Minecraft reached its sign-in and stopped there with an assertion, earlier the faster it ran (45 s, then 15 s). The assertion's strings, read from guest memory at the fault, said "PlatformIdentity_sony: invalid user id". A login event from `sceUserServiceGetEvent` and stubs for `sceNpTrophy2RegisterContext` and `sceNpUniversalDataSystemCreateEvent` (names found with `scripts/nid` by trying likely names) get it past; it then runs its menu at a much higher rate.
- **Coverage pass.** Untranslated exits had become the largest exit source (19.9 M per 40 s). See the list below.
- **The lock again.** Checking whether a trap address has a native took the machine lock on every host call (fixed with a lock-free list); the lookup table grew from 2^16 to 2^20 entries (misses at blocks already translated, which take the lock, went from 2.9 M to 0.6 M per 40 s); and stage 2 now maps only memory the guest can access, so releasing direct memory no longer needs a full rebuild (full rebuilds went from 7,756 to 2 per 40 s, vCPU kicks from 41,671 to 2; 570 stage-2 faults from stale TLB entries were handled by the host instead). Minecraft: 59 against 56 flips/s back to back, within the noise of single runs.

Minecraft, 40 s with statistics, after all of the above: 27.4 G instructions translated and 13.1 M interpreted; 23.1 M lookup misses (19.6 M of them host calls), 12.7 M untranslated exits. Most interpreted instructions are now `pcmpistri` (7.8 M), `roundss`/`roundps` (`0F3A 0A`, 0.9 M) and `call` through memory (`FF /6`, which is `push`), then 16-bit `div`, `shr r/m8, cl`, `cmpps`/`cmpss`. Host calls are now mostly `scePthreadRwlock{Rdlock,Unlock}` and `scePthreadMutex{Lock,Unlock}` (about 5.6 M per 40 s together). Three plain 45 s runs of Minecraft had no guest fault (2026-11-20), nor did the runs above.

What is left, measured: guest threads leave the VM about 900 thousand times a second (40 s of Minecraft: 22.6 M lookup misses, 21.4 M of them host calls, and 13.4 M untranslated exits). A sampling attempt (kicking every vCPU every 500 us) found the vCPUs almost always already out of the VM for an exit when the kick landed, so guest code runs in short stints between exits; host calls (`scePthreadRwlock*` and `scePthreadMutex*` lead) and the untranslated `pcmpistri` are the next targets, more than the quality of translated code.

**World loading (2026-11-20).** Measured as the seconds from choosing the saved world in Minecraft's Play screen to "Player Spawned" in its log, release build with the Metal renderer, headless, no profiler: 62 and 63 s before, 49 s after the first three fixes below, 30 and 31 s after eager sync, 24 s after faster syncs, 23 s with the bigger code cache. Found with the profile's new columns (CPU used, and time outside the VM, the interpreter, translating and host functions) and `sample`:

- **The profiler itself.** It took one global mutex several times per VM exit, so loads with profiling on took several minutes. Its counts, and the exit statistics, are now per thread and added up when reported.
- **Region checks.** `Memory::check` used as much CPU as all guest code: each handle remembered one region, and a thread moving between its stack, code, data and host function trap addresses looked the region up again under the shared region lock nearly every time. Handles now remember 8 regions.
- **Shared cache lines.** Each vCPU's flags (`running`, `inside`, `exits`, `old_pc`) were in arrays packed 8 vCPUs to a cache line and written on every entry and exit, and the pool user counts shared a line with the generation and epoch that every entry reads. Each vCPU's flags now have their own 128-byte slot. The lookup table also grew from 2^20 to 2^22 entries (64 MiB): misses at translated blocks, which take the machine lock, went from 1.08 M to 0.19 M per 70 s.
- **Eager sync.** Minecraft changes its memory map about 450 times a second while loading. Every change sent every running vCPU to the machine lock to sync (about 250 K slow entries per 70 s), where they queued behind translations (about 16 K a second, each holding the lock): most of the time the guest threads were not running was this wait. Now the thread that changes memory syncs the VM at once (`jit::sync_eagerly`, a hook in `memory::on_change`), and vCPUs enter without comparing generations; one that races ahead of the sync faults on a range not mapped yet, which the host interprets, or reaches a range unmapped a moment ago, as vCPUs already inside the VM could before. Slow entries went to 3.5 K per 70 s. `PS5SLOP_JIT_LAZY_SYNC=1` goes back to syncing on entry. Also: a vCPU whose TLB epoch is old adopts the new epoch without the lock (it flushes on entry), threads on the slow path retry the lock-free check while another thread holds the lock, and reclaiming evicted segments only tries the lock.

- **Slow syncs.** The profile now lists the JIT lock by call site (`#[track_caller]` on `machine()`): times taken, time waited for it and time held. In a 24 s load the eager syncs held it for 12.2 s (11.5 K syncs, about 1 ms each), translation for 3.4 s, so threads waited 25 s to translate. Each sync built SipHash sets of every region (thousands) to diff the region list against the last one, three times; it now diffs the sorted lists by merging (`sorted_diff`). Syncs hold the lock for 2.2 s per 24 s of loading (0.13 ms each), waiting to translate fell to 5.5 s, and the load from 30 s to 24 s.

- **A bigger code cache.** The cache was 13 segments of 8 MiB (blocks branched to the dispatcher with B, which reaches 128 MiB), and loading a world turned it over completely: 28 to 31% of translations were of evicted code. The runtime is now 1 GiB (all one TTBR1 L2 table maps): the cache has 118 segments, each starting with its own copy of the dispatcher and the verify-mode exit (`cache::write_stubs`), and chains that B cannot reach stay on the dispatcher. Pages are committed only when code is written. Loading: no evictions, no retranslations, 0.70 M translations instead of 1.0 M, waiting to translate 2.1 s instead of 5.5 s, the load 24 to 23 s.

After these, 70 s of loading: 59.7 M VM exits (58.4 M host calls, mostly `scePthreadRwlock*` and `scePthreadMutex*`; 20.3 M interpreter exits, mostly `pcmpistri`) and 1.16 M translations with 16 segments evicted, so the code cache is refilled about once a minute.

**Fixed: two threads mapping the same free range (2026-11-20).** After eager sync, world loads hit a guest Protection fault in 2 of 9 runs (0 of 8 with `PS5SLOP_JIT_LAZY_SYNC=1`). Cause: `sceKernelReserveVirtualRange`, `sceKernelMapDirectMemory` and `mmap` without `MAP_FIXED` (and new thread stacks and TLS) found a free range and mapped it in two steps, so two threads could choose the same range; a reserve then mapped over the other thread's new memory as no-access ("reserved"), and its next write faulted. Eager sync made each memory call longer, so the steps overlapped more often. `Memory::map_free` now finds and maps under the region lock (test `threads_mapping_free_memory_never_share_a_range`); 12 of 12 loads after that, 4 at a time. A guest fault now also prints the region at the faulting address and the recent region changes near it (`Memory::changes_near`).

**Open issue: a rare guest fault.** Minecraft sometimes stops with a guest fault in its own code: a divide by zero at `0xd58167`, or a null or text pointer read near `0xd5786b` and `0xbe4a6f6`, always reading zeros from the same object around `0x10438c8000`. Counted in 12 s runs (2026-11-20): 0 of 20 with the default build, 2 of 20 when every memory change rebuilt the tables and kicked the vCPUs (the behaviour before in-place changes), 2 of 12 with tier 2 at a count of 200, and 2 of about 12 with the 500 us kicks; none in the 45 s runs listed above. It appears when timing is disturbed (kicks, tier-up exits), which points at a race in the guest or in our HLE synchronisation that faster or different scheduling exposes, not at a translation: verify mode finds no difference there. Not solved. Update 2026-11-20: with the code cache sampler kicking vCPUs 100 times a second it became common (about 1 in 4 runs to the menu). One cause found: `sceKernelReleaseDirectMemory` of part of an allocation freed the whole allocation, so later allocations overlapped live memory; fixed, after which 1 of 12 runs still faulted (a write-protection fault in the guest's `memset` into direct memory). Direct memory is also not modelled as physical memory: two mappings of the same physical range get separate pages. Sharing them (`Memory::map_physical`, kept in the memory crate) made Minecraft fault at once, because it releases and reallocates the start of its own heap, so the PS5's release and allocation rules are not understood yet; mapping stays as before.

## Stopping a kicked thread (2026-11-22, late night)

When a thread was kicked out of the VM (`hv_vcpus_exit`) while its stop condition held (a save state asks threads to park, an exception is pending, the process exits), `Engine::run` returned at once without storing the vCPU's registers. The thread kept the x86 state of its last VM entry while memory already held everything the code had done since, so it ran that code again from stale registers when it went on. In GTA V's Performance mode a save stopped the world several times (the graphics queue was waiting on the CPU, see [savestates.md](savestates.md)), the audio mixer thread came back with a stack pointer that no longer matched its stack, and the game faulted on its stack canary right after the save and right after every load of that state.

A kicked vCPU's registers match no x86 instruction boundary, so a stop now waits for the next exit that stores them (a host call, an untranslated instruction, a fault), resuming the VM after each kick; only after 5 s (`STOP_GRACE`, longer than a save's 3 s stop limit) does it leave with the old registers, so a process exit still ends a thread that spins in translated code. Test: `a_thread_stopped_by_a_kick_leaves_with_registers_that_match_memory` (a counting loop kicked every 200 us; before the fix the register held 0 while memory held the count). A thread spinning on a lock held by a parked thread no longer parks, so such a save fails after 3 s and retries instead of saving a broken thread.

The same early return applied to pending exceptions (`sceKernelRaiseException`), whose handlers then ran on stale registers. Whether that is behind Minecraft's rare fault under kicks (above) is not checked.

## Tier 2

Off by default; `PS5SLOP_JIT_TIER2=N` compiles a block's region after the block ran `N` times, `PS5SLOP_JIT_TIER2=eager` on its first run (the test mode). Modelled on 86slopper's design ([its `docs/jit-tier2.md`](references.md)), phase 1, synchronous:

- **Counting.** A tier-1 block starts with a five-instruction prologue that counts down a word stored after the block (no flags touched); at zero it exits with `hvc #4` and the host compiles the region. The block's first word then becomes a branch to the region (or, when there is nothing better, past the prologue), the lookup table points at the region, and chains to the block reach it.
- **Regions** are the blocks the entry's direct branches reach on its 4 KiB page, up to 32 blocks and 512 instructions. Branches between them stay inside the region; other targets leave through chainable exits. Instructions tier 2 has no emitter for are emitted inline by tier 1, so a region does not stop at SSE or x87 code; a call, return or indirect jump ends a region block as in tier 1.
- **Flag demand.** A backward pass over the region finds, for each instruction, the flags code after it may read (exits count as reading all of them; instructions that may hand themselves to the interpreter too, so state is exact there). MOV, LEA and 32/64-bit ADD/SUB/AND/OR/XOR/CMP/TEST (register, immediate and memory forms) are emitted with direct operands and base+displacement addressing, and compute NZCV, PF and AF only when demanded: `cmp; jcc` inside a region is one `subs` and a `b.cond`.
- **Not done** from 86slopper's plan: the SSA IR with constant and copy propagation and redundant load removal, register allocation beyond the pinned guest registers, loop-invariant code motion, hot-path layout from counts, background compilation, x87 and SSE in tier 2, and regions across pages.

Checks: every interpreter-comparison test in `tests.rs` runs twice, with tier 2 off and eager (a deliberate bug, a missing `cfinv` after additions, made one fail); `list_walk_matches_the_interpreter` covers a loop region. Verify mode checks regions too (see below). Minecraft in eager mode ran 45 s without a fault (at 1.6 flips/s: compiling a region for every block is slow).

Measured (2026-11-20, Minecraft, back to back): off 58.9 and 57.6 flips/s, count 1000 70.6 and 54.1, count 200 61.7. In 40 s at count 1000, 21 thousand regions were compiled and 6% more guest instructions ran (30.9 G against 29.1 G). The difference in frame rate is within the noise, as expected while exits dominate; tier 2 stays off by default until it shows a gain (and while the open issue above is not understood).

## Where the time goes now

`sample` on the interpreter while ScreenTester5 draws its first frame (2026-11-19, release build): decode and instruction fetch take about 40% of the busy time, memory checks (region lookup and permissions) about 25%, executing instructions about 20%, and copies inside HLE `memset`/`memcpy` about 10%. Translated code removes the first two.

## VM layout

**Guest physical (IPA) space**, 40 bits (the most this machine allows, 1 TiB):

- Each `Memory` region is mapped (`hv_vm_map`) at an IPA equal to its guest address, from the same host memory the interpreter uses. Unmapped guest addresses are unmapped at stage 2 too.
- Regions without read or write access are not mapped at stage 2 either (since 2026-11-20).
- `0xFE_0000_0000 .. 0xFF_0000_0000` is reserved for the runtime and never holds guest memory (see [memory.md](memory.md)).

**Stage 1**, set up by us:

- TTBR0: guest addresses, 40 bits (`T0SZ = 24`), 4 KiB granule, identity-mapped onto the IPA. A region's protection becomes the page's: no access is an invalid entry, read-only is AP read-only at EL1, read-write is read-write. Execute permission is the translator's business (it reads guest code through `Memory`).
- TTBR1: the runtime at `0xFFFF_FF80_0000_0000`: exception vectors, entry and exit code, per-vCPU state blocks and stacks, the block lookup table, the code cache, and the TTBR0 page tables themselves.

**Execution level:** translated code runs at EL1 with the runtime, so the MMU checks guest accesses (EL1 permissions), and a bad access is a synchronous exception our vectors turn into an exit. `ACTLR_EL1.EnTSO` is set on every vCPU.

**vCPUs:** one per guest thread, created on that guest thread's host thread (HVF binds a vCPU to its thread). The VM allows 64; a thread about to block gives its vCPU back while a running thread has none (see "Astro Bot's loading" above).

**Memory changes** (`mmap`, `munmap`, protection changes) bump `Memory`'s generation. Since 2026-11-20 most changes are made to the active TTBR0 tables in place, while vCPUs run on them: new ranges are added (entries go from invalid to valid, and invalid entries are never cached in a TLB) and removed ranges are cleared, without a TLB flush or kick. A vCPU that still holds a removed entry in its TLB reaches the same physical address, because stage 1 maps every guest address to itself, and stage 2 (which HVF changes for every vCPU) maps that to the current pages or to nothing, a fault the host handles by interpreting the instruction. Stage 2 maps only regions the guest can read or write. Only a change that leaves a writable address mapped read-only takes the full path below: tables rebuilt in the other pool, epoch bumped, vCPUs kicked. Test: `unmapped_and_read_only_memory_faults_after_a_sync`. Large mappings and unmaps replace the host pages under a range (a fresh `MAP_FIXED` mapping; see [memory.md](memory.md)), and the VM's stage 2 still points at the old pages; `Memory::take_fresh` lists those ranges, and the sync maps them again. Without this, Minecraft's start-up wrote to pages the interpreter and host functions never saw (found with verify mode). With the JIT on, the thread that changes memory syncs right away (see "World loading" above), and a vCPU enters without comparing generations unless the tables are being rebuilt. Without that (`PS5SLOP_JIT_LAZY_SYNC=1`, and in tests), before a vCPU enters the VM it checks, without a lock, that the tables mirror the current generation and that its TLB was flushed at the current epoch; otherwise it takes the machine's lock, brings the stage-2 mappings and TTBR0 tables up to date and flushes its TLB if the epoch changed. A change made while other vCPUs run kicks them out (`hv_vcpus_exit`) so they resync.

## Translated code

- x86 `RAX`..`R15` live in `x0`..`x15`, so exits read and write them directly.
- `x16` holds the guest RIP at block ends and exits; `x16`..`x18` are the dispatcher's scratch (blocks use `x17`/`x18` for flag work too).
- `x19`..`x23` are the translator's temporaries, `x24` counts translated guest instructions, `x26`/`x27` hold the last result and the operands' XOR (for PF and AF, computed when needed), `x28` points at the lookup table and `x29` holds the FS base.
- NZCV holds SF, ZF and OF, and CF inverted (ARM's borrow convention), so every x86 condition is one ARM condition (`jbe` is `LS`, `ja` is `HI`). Narrow (8- and 16-bit) operations work on values shifted to the top of a W register, so NZCV fits their width.
- Flags are only computed when a later instruction in the block (or the block's end) may read them. Where the interpreter keeps or computes undefined flags (AF kept after shifts, OF after multi-bit shifts computed as for a count of 1), the JIT does the same, so the two agree exactly. Until 2026-11-19 the JIT kept the old OF after multi-bit shifts; verify mode found the difference in Minecraft.
- A block ends with a jump to the dispatcher, which looks the next RIP up in a direct-mapped table (2^22 entries since 2026-11-20, at the end of the runtime region, Fibonacci hash; blocks branch to the copy of the dispatcher at the start of their code cache segment, within reach of a B instruction) and exits with `hvc #1` on a miss. Instructions not translated yet end the block with `hvc #2`; the host runs them in the interpreter (up to 64, until one could start a block) and re-enters. A call into the HLE trap region is a lookup miss the host recognises.
- A fault in translated code maps the host PC back to the guest instruction, which the interpreter runs again. Translations do their memory accesses before writing registers, so a faulting instruction has not changed guest state.
- DF lives in the vCPU's context block after the YMM registers, as 0 or all ones, so a string instruction's step is `(size ^ df) - df` without touching NZCV. Entry and exit copy it to and from RFLAGS, so `cld`/`std` in the interpreter and in translated code see each other.
- An instruction can also hand itself to the interpreter at run time: it branches, before changing any guest state or NZCV, to a stub at the end of the block that takes the instructions not run off the count and exits with `hvc #2` at its own RIP. `div` and `idiv` do this for division by zero, quotients that do not fit and 64-bit dividends wider than RAX.

Verify mode could not check world loading: it never evicts, so its code cache fills about 17 s after start and new code is interpreted (150 s of start-up in verify mode showed 0 differences). These are checked two ways: `crates/jit/src/tests.rs` runs a program of each kind (integer and vector, with the edge cases: zero counts and sources, a failing `cmpxchg`, a `div` that needs the interpreter, NaN and overflowing conversions) in the JIT and in the interpreter and compares registers, flags and memory; and Minecraft's start-up in verify mode shows no differences (2026-11-19, 81 s to the `sceAgcCreateShader` stop), nor do 30 s each of ScreenTester5 and DriftCheck. After the second pass `tests.rs` has three more programs (bit and string instructions, including DF set by translated `std` and read back across an interpreted `stc` and `pushfq`; shuffles and conversions with NaN, ties and overflow; lane moves), and two deliberate bugs (a wrong `crc32c` encoding with a fixed string step, and a wrong `vpermq` lane or rounding mode) made them fail. Balatro's start-up in verify mode shows no differences (150 s to its stop). Minecraft's showed one difference in two of three runs, each time in a block this pass did not touch that reads a lock word (`mov rax, [rdi+0x28]` and a `lock cmpxchg` loop): another thread wrote the word between the interpreter's run and the JIT's, which verify mode cannot tell from a bug. The third run had none. The interpreter is the oracle, so where it is wrong about real hardware the JIT is wrong the same way.

Not yet (2026-11-20): 8- and 16-bit `adc`/`sbb`, 8- and 16-bit rotates by CL, 16-bit `div`, signed 64-bit `idiv` with RDX not the sign of RAX, `rcl`/`rcr`, `push r/m16`, string instructions with an address-size or segment prefix, LOCK on other instructions (`not`, `neg`, `adc`), 16-bit `bt` forms, `pcmpistri` and the other SSE4.2 string operations, `vfmaddsub`/`vfmsubadd`, `vpermd`/`vpermps`, and the rest of x87 (`fcom` family, `fprem`, transcendental functions, `fnstenv`/`fnsave`). In 40 s of Minecraft the interpreter now runs 13.1 M instructions, most of them `pcmpistri` (7.8 M); in 25 s of Balatro 5.9 M, most of them packed FMA forms counted before the third pass and `pcmpistri`.

**Library functions in the VM.** `memset`, `memcpy` and `memmove` have native versions in the runtime region, and since 2026-11-20 `pthread_getspecific`/`scePthreadGetspecific` (keys below 128, whose values HLE keeps at the thread pointer plus `0x400`; others leave with `hvc #3` for the host function), `scePthreadGetthreadid` and `pthread_self`/`scePthreadSelf` (from the FS base in x29). When a block takes a native's lookup slot, the next miss at that trap address puts the native back. The kernel registers their trap addresses when the JIT is on, so the dispatcher sends guest calls straight to them, and they return as the guest's `ret` would. A fault inside one falls back to the host function at the same address, which reports it as before. Verify mode uses the host versions. ScreenTester5's flash mode called `memset` 3.2 M times in 5 s; each was a VM exit before.

Block ends with a known target are chained: the branch to the dispatcher is patched to go straight to the target block once it is translated (in verify mode, only between blocks that passed their checks).

**The lookup table and races.** The host replaces a slot (`enter`) in three stores: tag cleared, code address, new tag. The dispatcher reads the tag, checks it, reads the code address, then reads the tag again and checks it before jumping; loads stay in order under TSO, so two matching reads mean the code address belongs to that tag. Until 2026-11-19 it read the tag only once, before the code address: a thread could check the old tag and jump to the new occupant's code, running another address's block. Minecraft crashed in a different place nearly every run (wild jumps into stacks, writes through small integers); with the second check, four runs of 45 s ran their full length without a crash. Found by elimination: the crashes went away in trace mode (no lookups inside the VM) but not without the native library functions.

## Code cache eviction

The code cache (about 940 MiB since 2026-11-20, about 110 MiB before) is split into 8 MiB segments (`cache.rs`), each starting with its own dispatcher stub. Code fills one segment at a time and never straddles two; a block that does not fit is translated again at the start of the next free segment. Minecraft filled the whole cache within seconds of starting world creation (973k blocks, 5.7M guest instructions, about 113 bytes of ARM code per block), after which everything new ran in the interpreter.

When no segment is free, the coldest full one is evicted: the lowest score, then the oldest. A sampler thread kicks every running vCPU every 10 ms (`hv_vcpus_exit`); each cancelled exit adds one to the score of the segment its PC was in, and scores halve at every eviction round, so they mix how often and how recently a segment ran. This costs nothing in translated code; per-block counters would cost a load, an add and a store per block and contend on hot blocks that many threads run. One eviction is always kept ahead, so a drained segment is usually ready when the current one fills. Hot blocks from an evicted segment are translated again, into the current segment, when next reached.

Evicting a segment takes its blocks and regions out of the lookup table and puts every patched branch into or inside it back to its original word (each patch records the word it replaced, and the code it leads to). The segment is reused only when every vCPU that was inside the VM at the eviction has left it once, and no vCPU still holds an address in the segment from its last exit (a cancelled run it will resume, or a fault whose RIP it looks up). vCPUs check for this on each entry while a segment drains. A vCPU that cannot get a segment interprets until one is free. `PS5SLOP_JIT_SEGMENTS=N` uses only the first N segments (at least 2), to test eviction.

Verified: Minecraft reaches its menu and Balatro its title with 2 and 3 segments (Minecraft evicting all the time), and Minecraft's world creation and loading run past the point where the cache used to fill (2026-11-20). Not measured yet: how often segments are evicted in a long session, and what retranslation costs.

## Trace mode

`PS5SLOP_JIT_TRACE=1` sends every block's exit to the host, without lookups or chaining inside the VM, and keeps the last 64 blocks each thread entered; a guest fault prints them ("blocks before: ..."), which shows where a wild jump came from. It is slower, and timing changes, so races may hide in it.

## Statistics mode

`PS5SLOP_JIT_STATS=1` prints, when the process ends (end the run with `--dump-frame PATH --after SECONDS`; a `timeout` kill prints nothing), the translated and interpreted instruction counts, exits by kind, the interpreted instructions by opcode and by address (with their bytes, for `llvm-mc --disassemble`), and host calls by function (`PS5SLOP_JIT_STATS_TOP=n` lists the top `n` addresses and functions instead of 20). Since 2026-11-20 the exits also count misses at blocks already translated (table collisions), misses at untranslatable code, full table rebuilds and VM entries that took the lock. This is how the next instructions to translate are chosen.

## Verify mode

`PS5SLOP_JIT_VERIFY=1` checks the first 4 runs of every block against the interpreter: the interpreter runs the block with `Memory`'s write journal on, its writes are undone, the translated block runs alone, and registers, RIP, arithmetic flags and the bytes the interpreter wrote are compared. Differences are printed with the block's bytes, and execution carries on from the interpreter's state. Since 2026-11-20 the x87 state is compared too, and a block that hands an instruction to the interpreter part way (a bail) is finished in the interpreter before the comparison; before, every bail showed up as a difference. Minecraft, 55 s in verify mode after the third pass: 7 differences, all in blocks that read a word another thread changes (`lock cmpxchg` and `lock xadd` loops, a spin on a flag).

Since tier 2, verify mode keeps the interpreter's state after every step of a region (up to 4,096 steps, while it stays on the region's instructions) and compares the translated code's state with the step its instruction counter reached. Blocks keep one journal and compare at their end; a block that bails part way is not compared. Minecraft with `PS5SLOP_JIT_TIER2=50`, 55 s in verify mode: 3 differences, all races of the kinds above (one a list walk reading nodes another thread changes, reproduced without a difference in `list_walk_matches_the_interpreter`). Verify mode is much slower with regions (3 flips/s). A difference on a lock word can break the program, because verify mode continues from the interpreter's state and writes its values back (one run ended in the title's own abort after such a difference). While a block is being checked it exits through a stub that leaves the VM (`VERIFY_EXIT`), so each check runs exactly that block; once it passes, a second copy with ordinary exits is entered in the lookup table and chained to other checked blocks, so verify mode runs at the JIT's speed (Balatro: the same frame rate as without it). Writes only the JIT made are not caught, and a block that reads memory another thread changes between the two runs shows up as a difference (lock words, counters).

## Stages

A. (done) **The VM itself:** mapping `Memory` at stage 2, TTBR0 tables from its regions, the runtime region, vectors, entering at EL1 and exiting with `hvc`. Tested with hand-written AArch64 that reads and writes guest memory, faults on read-only and unmapped pages, and exits.
B. (done) **Blocks and the dispatcher:** translate a basic block of guest code at a time, look blocks up by guest RIP inside the VM, exit to the host on a miss. HLE calls are exits (the trap region stays unmapped, so a call into it faults). Instructions the translator does not handle yet end the block, and the host runs them in the interpreter.
C. **Integer instructions** with flags computed lazily, then **SSE/AVX** on NEON. The FEX ASM tests run against the JIT as they do against the interpreter.
D. **Speed:** block chaining, return prediction, in-VM paths for the hottest HLE functions, measured against the interpreter.

## Open questions

- Self-modifying and generated code: pages holding translated code become read-only in TTBR0 and a write faults to the host. No PS5 title known to need it yet.

## Ideas (not planned)

- **A persistent translation cache** (vic, 2026-11-20), like Ryujinx's PPTC: save translated blocks to a file per module and load them on the next run, so launches after the first skip translation and evicted code is read back instead of translated again (28% of world-load translations were of evicted code). Saved profiles would let tier 2 recompile hot regions ahead of time instead of stalling a guest thread. It needs relocatable output (relocation records for every branch into the runtime and chain site), keys per module (a hash of its bytes, module-relative RIPs) and only file-backed code. Whole-file AOT like Android's ART is not the aim: finding all code in an x86 binary is undecidable, so cache what has run. The cache is derived from the game, so it lives in the user's data folder, never in the repo.
