# HLE: the kernel interface and system libraries

How guest code reaches host code, and what we implement. `crates/hle`.

## How a call reaches the host

- Every import binds, at load time, to its own 16-byte slot in a **trap region** at `0xFF_0000_0000` (our choice, see [memory.md](memory.md)). The region cannot be read, written or executed.
- When guest code jumps there, the interpreter stops with `Exit::Trap(address)` before decoding anything. The slot names a `(library, NID)` pair; if a host function implements it, it runs with the SysV AMD64 arguments (`rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`), its result goes to `rax`, and the return address is popped from the stack, as a `ret` would.
- Imports with no host function still get a slot. Calling one stops the process with "unimplemented *library* function with NID *x*" and the caller's address, instead of a jump to address 0. `ps5slop run` reports how many imports are unimplemented before it starts, and lists them (library and NID) when the environment variable `RUST_LOG=ps5slop=debug` is set. With `PS5SLOP_UNIMPLEMENTED_ZERO` set, such calls return 0 instead, each with an `UNIMPLEMENTED (returning 0)` line naming the import, its first four arguments and its caller (see [debugging.md](debugging.md)).
- A raw `syscall` instruction stops the process with an error. We serve the kernel through libkernel's functions, not its system call numbers.

A JIT can keep the same scheme: a trap region is just memory it never maps executable.

## Threads

Each guest thread runs the interpreter on its own host thread (see [decisions.md](decisions.md)). `hle::Kernel` holds what they share: the stub table, the kernel objects, the thread records, the guest's stdout and stderr, and the process's exit state. A thread checks for process exit every 65,536 instructions, and a host function that blocks (a mutex, a join, a condition variable) wakes every 20 ms to check too. The process ends at `exit`, at the first guest error in any thread, or when its last thread ends.

A host function can also redirect the CPU instead of returning (`Outcome::Resume`): `pthread_once` uses that to call the guest's init routine with a return address in our trap region, so the host takes over again when the routine returns.

## errno

Each thread's errno lives in its thread control block, at the thread pointer plus `0x800` (our choice); `__error()` returns its address. The values of thread-specific keys 0 to 127 live at the thread pointer plus `0x400` (our choice, so the JIT's native `pthread_getspecific` reads them without leaving the VM); higher keys stay in a host table. POSIX-style functions that fail set it and return -1. The values are FreeBSD's (`hle::errno`), assumed rather than verified for Orbis. The pthread functions return error numbers directly, as POSIX says.

**Variables.** Some imports are data, not functions: libkernel's `__stack_chk_guard` is read through its GOT entry, although OpenOrbis's stub declares it a function. So the symbol type cannot be trusted; the HLE layer knows its variables by name and binds them to readable memory in a data region next to the trap region.

**Direct memory (2026-11-20).** `sceKernelReleaseDirectMemory` frees exactly the range given, splitting an allocation it cuts (it used to free every allocation it touched). Since 2026-11-21 mappings share the bytes of their physical range: direct memory is one host object, a map puts its pages at the mapping's offset (`Memory::map_physical`, `map_free_physical`), an allocation zeroes its range (`zero_physical`), and a range past the end of direct memory or an unaligned offset falls back to private zeroed pages. Reason: GTA V maps the same physical pages at two addresses during its Story Mode load and remaps them often before its title, which fresh pages per mapping lose. It did not cure GTA V's faults (below). Balatro, Isaac, Minecraft's title, Superliminal's menu and Astro Bot's title draw as before (2026-11-21). `RUST_LOG=hle::dmem=debug` logs allocations, frees, maps and unmaps of direct memory, mappings of a range already mapped elsewhere, and how much live data a fixed map replaces. The offset is recorded per mapping, though, and `sceKernelVirtualQuery` reports it with the allocation's memory type, in shadPS4's `OrbisVirtualQueryInfo` layout (offset at 16, type at 28, kind bits at 32, name at 33; we used to write no offset and the name at 36). Minecraft's allocator frees a block by querying its mapping, reserving over it and releasing the offset the query gave; with offset 0 it released the wrong memory and leaked about 1 to 2 GiB a minute, which ran out after 13 minutes of play (see [debugging.md](debugging.md)). Releasing direct memory also unmaps every mapping of it, as shadPS4 does on the PS4 (unverified for the PS5); Minecraft's other free path queries and releases without unmapping, and those mappings used to stay, about 0.8 GiB of them after 10 minutes. A release or map of direct memory that is not allocated is reported once on stderr, as are allocation and mapping failures.

**pthread handles.** Mutexes, mutex attributes, condition variables, read-write locks and thread attributes are 64-byte blocks from our guest heap (see `new_handle`); destroying one gives its block back. Before 2026-11-20 they were never freed, and Minecraft, which makes and destroys about 1200 mutexes a second while in a world, grew the heap by about 8 MiB a minute.

**System dialogs and PSN.** We are always signed out of PSN (`sceNpGetState` reports state 1). libSceMsgDialog and libSceSigninDialog (`dialog.rs`) show nothing: an opened dialog is finished at once, a sign-in dialog as cancelled by the user, a message dialog as if its first button was pressed, and a user message's text goes to stderr. Status values (0 none, 1 initialized, 2 running, 3 finished), results (0 OK, 1 cancelled), the message dialog's result struct and the PS4 parameter offsets (mode at 56, user message parameters at 64, their text at 8) come from the OpenOrbis headers; the sign-in result layout (the result first) is a guess, and none of it is checked on a PS5. `sceNpGetAccountCountryA` answers "us"; account id, authorization codes, Plus checks and reachability fail with ENOSYS. With these, Minecraft's Play button reaches the world list and the world creation screens (2026-11-20).

**GTA V's settings (2026-11-23).** The game keeps its settings (graphics mode and the rest of the pause menu's Settings) in the save `SAVEDATAPROFILE`, file `Profile`, written through `sceSaveDataPrepare`/`Commit` whenever a setting changes. At boot it searches for that save and reads `mtime` from the search result's parameters (offset 0x508 of the PS4 `OrbisSaveDataParam` layout, filled in by the system). ### libSceAvPlayer

A player with no decoder, which plays Astro Bot's logo movie through as 3 s of black (2026-11-21). Layouts are what Astro Bot's own code reads, found by disassembling it locally (allowed for a title's own code, see [legal.md](legal.md); nothing from it is committed):

- `sceAvPlayerInit(init_data)`: the init data holds two blocks of an object and four functions (memory replacement: allocate, free, allocate texture, free texture; then file replacement), then the event object at +0x50 and callback at +0x58, the language pointer, the priority (705) and the frame buffer count (6). We return a 64-byte guest block keeping the event callback and the texture allocator.
- The event callback `(object, event, source, data)` acts on "ready" (2): it calls `StreamCount`, then `GetStreamInfo(handle, i, info)` for each stream into a 32-byte buffer (writing more trips its stack protector), takes a stream whose type (u32 at 0) is 1 and reads its width and height (u32s at 8 and 12) and duration (u64 at 0x18), then `EnableStream`. We report one 1920x1080 stream of 3 s. With no streams the title kept zero sizes and its texture creation asserted (`nativeTex.IsValid()` in `GfxSceneDynamicTexture.cpp`).
- `AddSource` calls back "ready", `Start` calls back "play" (3). `GetVideoDataEx(handle, info)` then returns frames: the title reads the data pointer at 0, the time stamp in ms at 0x10, the height at 0x1c, four crop offsets from 0x2c and the pitch at 0x3c, which it uses as the width; we also fill the width at 0x18 and the aspect ratio at 0x20. Frames are one NV12 buffer from the title's texture allocator, filled with black, with time stamps 33 ms apart. After 90 frames the callback gets "stop" (1) and `GetVideoDataEx` returns false; the title then pauses, resumes, checks `IsActive` (0), stops and closes the player and moves on.
- Event numbers are shadPS4's from memory; "ready" = 2 agrees with what the title checks. The fields between the aspect ratio and the crops (0x24, 0x28) and after the pitch are unknown and left 0.

Real playback would need a decoder for the title's movies (format not looked at).

### libSceFont

The engine draws its own text with libSceFont: it opens its font files with `sceFontOpenFontMemory` and the system font sets with `sceFontOpenFontSet`, measures with `sceFontGetRenderCharGlyphMetrics` and renders single glyphs into its own surface with `sceFontRenderCharGlyphImageHorizontal`. FreeType (the `freetype-rs` crate, built from its bundled source) loads the faces, measures and rasterises; glyphs are 8-bit coverage written into every byte of a surface pixel, keeping the larger value where glyphs overlap. Every font set is the Noto Sans JP stand-in (below). Libraries, renderers, fonts and glyphs are blocks from our guest heap, so titles get real pointers; their bytes stay zero. Prototypes, error codes and the public structure layouts (glyph metrics, render surface, render output, horizontal layout) come from shadPS4's `font.h` (see [references.md](references.md)), unverified for the PS5. **Observed:** Astro Bot renders "No translations" at 64 pixels with sensible glyph sizes and advances. Not done: the text layout calls (`sceFontCreateString`, the writing lines, the character queries; Astro Bot imports them but has not called them yet), which want HarfBuzz for shaping; effects (slant, weight) are accepted and ignored; vertical rendering; glyph outlines.

### System fonts

`font_settings.xml` names a font for each text style and language: either a file in `/app0/data/common/font` or a system font set, often both. The engine loads the files whatever the set, and the ones that are system fonts (`SIE-ShinGoPr6N-Heavy.otf`, `FuturaStd-Medium.otf`, `HeiseiMaruGo.TTF`, ...) are not in the package: a console has them (vic). So `/app0` lookups of these names that find nothing in the title get an open-source stand-in from the fonts folder (`--fonts DIR`, default `~/Library/Application Support/ps5slop/fonts`, filled by `scripts/fetch-fonts`): Noto Sans JP for SIE ShinGo and font sets, M PLUS Rounded 1c for Heisei Maru Gothic, Jost for Futura (and Jost Italic for Mohr). All are under the SIL Open Font License and are never committed. A file the title does have always wins. Weights are not matched: the variable fonts load at their default instance.

**Finding names for NIDs.** When a program stops at an unimplemented NID, we hash candidate names ourselves (function names from public API headers, such as the OpenOrbis headers) until one matches. That table stays local; we do not commit or import NID-to-name databases. Errors and `RUST_LOG=ps5slop=debug` name an import when we know the name: any function we implement, in any library, and the names in the file `PS5SLOP_NAMES` points to. `scripts/names > references/names.txt` writes such a list from the macOS SDK and OpenOrbis headers (gitignored). For Balatro it names 287 of 566 missing imports.

## Exceptions (libkernel_unity)

Unity's garbage collector stops the other managed threads with `sceKernelRaiseException(thread, 30)` after installing a handler for 30 with `sceKernelInstallExceptionHandler` (names found by hashing guesses; prototypes read off the calls). The handler acknowledges with a semaphore and then waits on an event flag until the collector restarts it. So the handler has to run on the target thread, while that thread is stopped, also when it is blocked in a host function.

- A raised exception is queued for its thread, and every vCPU is kicked so the thread leaves translated code (`exception.rs`). The thread's run loop, and `Env::call_guest`, deliver it before running guest code again.
- Delivery writes the interrupted registers below the stack pointer (past the red zone) and calls `handler(signal, context, context)` on the thread's own stack, so a scan of the stack sees them. The context is FreeBSD's amd64 `mcontext_t` layout starting at byte 64. **Observed:** Superliminal's handler reads the stack pointer at byte 248 of the context (found by filling slots and bisecting which one stopped the collector's abort; 248 is `mc_rsp` past 64). The rest of the layout is assumed.
- A thread blocked in a host function gives up the wait: condition variable waits and sleeps return early (POSIX allows it for the first; the second is our choice), and the other blocking calls (mutexes, rwlocks, semaphores, event flags, event queues, joins, `pthread_once`) return with the CPU untouched, so the call starts again after the handler, as `SA_RESTART` would. Timeouts written back as "time left" are updated first.

Verified: Superliminal runs several collections, each stopping one or two threads, and goes on loading. Not verified: what Orbis passes besides the context, and whether a real console restarts these calls.

## Asynchronous file reads (APR)

The PS5 reads files through command buffers: `sceKernelAprResolveFilepathsToIdsAndFileSizes(paths, count, ids, sizes, failed)` turns paths into 32-bit ids and 64-bit sizes, libSceAmpr builds a buffer of `ReadFile` commands, and `sceKernelAprSubmitCommandBufferAndGetResult(buffer, priority, result, id)` runs it. We keep the commands on the host, keyed by the guest address of the command buffer object, whose layout we never touch, and run the reads synchronously when the buffer is submitted. The result (8 bytes) is written as zero and submission ids count up. `ReadFile` takes `(buffer, ?, ?, file, dest, size, offset)` with the offset as the first stack argument: the size matched the file Superliminal asked for, and its reads at non-zero offsets load the right data. The two unknown arguments are pointers into the command buffer object. Names were found by hashing guesses; SharpProspero's documentation (prose only) gave the shape of the command buffer and the invalid id `0xFFFFFFFF`. Unverified beyond Superliminal. GTA V adds a resolve with a path prefix, and a command that writes a value to an address once the reads before it are done (see the GTA V section below).

## The guest file system

Guest paths resolve through a small mount table (`crates/hle/src/vfs.rs`): `/app0` is the title, read-only: a host folder, or a package's image served through the `ImageFs` trait (see [packages.md](packages.md)); `/data` is a writable per-title folder on the host, by default `~/Library/Application Support/ps5slop/<title id>/data`, or the folder's name when there is no title id (`--data DIR` picks another). Saves (`savedata`) and `/temp0` (`temp`) sit next to the data folder: as siblings with those names when the folder is called `data`, as `DIR.savedata` and `DIR.temp` otherwise, so data folders side by side never share saves. Descriptors and FILEs hold a `GuestFile`, a host file or a file in an image, so reads, seeks, `fstat` and `getdents` work on both. `sceNgs2ParseWaveformFile` still uses host paths (`Vfs::resolve`), so it cannot read files from a package yet. Anything else does not exist, and paths that climb out of a mount with `..` are refused. What a real PS5 title sees under `/data`, and which other mounts it expects (`/savedata0`, `/temp0`, `/hostapp`), is unverified.

## How a process starts

The entry point gets what shadPS4's `RunMainEntry` passes, which OpenOrbis's startup code (`_start` in its `crt1.o`) relies on:

- `rdi`: the entry parameter block `{ i32 argc; u32 pad; char *argv[]; }`, with `argv` ending in a null pointer. We pass one argument, `eboot.bin`.
- `rsi`: a loader teardown callback. The PS5 homebrew template's `_start(process_parameters, loader_teardown)` registers it with `atexit`, so it is called during `exit` and must return. Ours is the internal `ps5slop::loader_teardown`, which does nothing. What the real loader does in it is unknown.
- `rsp`: 8 bytes off a 16-byte boundary, with the parameter block's first two words (argc and `argv[0]`) copied to the top of the stack.
- FS base: the main thread's thread pointer. Static TLS uses the x86-64 "variant II" layout: FS points at a word that holds its own address, and the executable's `PT_TLS` image sits just below it.

Status: matches both sources and gets vic's OpenOrbis `eboot.bin` through its startup code into libc, where it stops at the first SSE instruction (`movd`). What the real Orbis kernel puts on the stack beyond this (environment, auxiliary vector) is unknown; shadPS4 notes that it pushes more.
