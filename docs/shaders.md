# Shaders

How PS5 shader programs become Metal Shading Language. The code is the `gfx10` crate (`crates/gfx10`). The GPU plan around it is in [gpu.md](gpu.md).

PS5 titles ship GPU programs as AMD GFX10 machine code. The PS5 GPU is gfx1013: GFX10.1 (RDNA1) plus BVH ray-tracing and MSAA-load instructions (LLVM's `GCNFeatures.td`, see gpu.md). The crate decodes that code, prints it in LLVM's syntax, and translates it to MSL.

## The `.ags` container

What Balatro's 42 files in `shaders/*.ags` look like (all of it observed by reading them; nothing here is documented anywhere we know of):

- An ELF64 little-endian file, `e_type` EXEC, `e_machine` 0xE0 (`EM_AMDGPU`), no program headers, six sections: `.shader_text`, `.shader_header`, `.metadata`, `.cfg`, `.shstrtab` and the null section.
- `.shader_text` (alignment 256) holds the machine code from offset 0, padded with `s_code_end` and zero words, then a trailer that starts with the magic `sl00` and ends with the ASCII string `barefoot` and a 32-bit hash. The hash equals the value the header gives the checksum SH register (`0x2C06` in pixel shaders, `0x2C80` in the vertex ones), so it is presumably the program checksum. No header field holds the code size; `Ags::code()` cuts at `sl00`.
- `.shader_header` starts with the AGC shader header `sceAgcCreateShader` takes (magic `0x34333231`, version `0x18`). Its pointer fields (user data 0x08, CX registers 0x18, SH registers 0x20, specials 0x28, input semantics 0x30, output semantics 0x38) hold offsets relative to the field itself, as `crates/hle/src/agc/shader.rs` relocates them, and all point inside the section. The code pointer at 0x10 is 0 in the file. 0x40 is the header section's size and 0x44 the text section's size. 0x5A is the stage (1 pixel, 2 the NGG geometry stage that runs vertex programs), 0x5B the number of CX registers, 0x5C the number of SH registers. Register tables are `(register, value)` pairs of `u32`, register numbers relative to 0xA000 (context) and 0x2C00 (SH).
- The SH tables hold the program address pair (0 in the file), `RSRC1`, `RSRC2` and the checksum register, the latter twice with different values (the first value is not understood). The CX tables hold what Mesa's register database calls `SPI_SHADER_Z_FORMAT`, `SPI_SHADER_COL_FORMAT`, `SPI_PS_INPUT_ENA`/`ADDR`, `SPI_PS_IN_CONTROL`, `SPI_BARYC_CNTL`, `DB_SHADER_CONTROL`, `CB_SHADER_MASK` for pixel shaders.
- `.metadata` starts with another `sl00` block that contains the compiler version (`8.0.0.0 build 506 revision ...`) and the names of resources and semantics (`samp0`, `colorMap`, `TEXCOORD`, `main`). `.cfg` is binary and not looked at.
- Every shader is wave64: the pixel shaders have `SPI_PS_IN_CONTROL.PS_W32_EN` clear and the vertex shaders use 64-bit `exec` arithmetic. `Ags::wave64()` reads that bit.

`Ags::request` builds a translation request from the file's registers, so tests and the `ags` example (`cargo run -p gfx10 --example ags -- file.ags`) can translate files without the HLE layer.

## Decoder and printer (milestone 1)

`decode::decode` turns words into an `Inst`: the opcode (`opinfo::OpInfo`: name, format, operand types) and the format's fields (`decode::Kind`). It covers SOP1, SOP2, SOPK, SOPC, SOPP, SMEM, VOP1, VOP2, VOPC, VOP3 (a and b), VOP3P, SDWA, DPP16, DPP8, VINTRP, DS, MUBUF, MTBUF, MIMG (with NSA), EXP, FLAT, GLOBAL and SCRATCH, with literal and inline constants. VOP1, VOP2, VOPC and VINTRP opcodes promoted to VOP3 are found by their VOP3 number.

The opcode table `src/opcodes.rs` is generated by `tools/gen_opcodes.py` from Mesa ACO's `aco_opcodes.py` (MIT) and edited by the script for gfx1013: it drops what GFX10.1 lacks (GFX10.3's `fma_legacy`, `csub`, the dot instructions, `addtid` loads), renames to LLVM's mnemonics (`v_add_nc_u32`, `v_add_co_ci_u32`, `v_cmp_ne_*` for integers) and adds what ACO leaves out (`v_illegal`, `image_gather4h`, the `cd`/`g16` sample variants).

`print::print` writes LLVM's syntax. `print::print_checked` also says whether LLVM's disassembler accepts the encoding: it rejects reserved operand codes, misaligned or out-of-range register ranges, modifiers an opcode does not take, unused fields that must be zero and so on. These rules were found by comparison with llvm-mc, not from documentation.

### Verified against llvm-mc

The oracle is `llvm-mc --disassemble -triple=amdgcn -mcpu=gfx1013` (LLVM 21.1.8 in the dev shell). `tests/llvm.rs` runs it when it is on PATH:

- **Balatro**: all 42 shaders, 9246 instructions, decode and print exactly as llvm-mc does in wave64 mode.
- **Generated encodings**: random encodings per format, with known and random opcode numbers, random fields and both wave sizes. A case passes when both reject it, or both print the same text, or LLVM's text does not assemble back to the same words with `llvm-mc -show-encoding` (LLVM's disassembler then printed a fallback for an encoding it does not support, mostly MIMG with mismatched sizes and reserved bits). The test fails on a text difference or an encoding only LLVM accepts. Default 300 cases per format (6000, about 9 s); `GFX10_CASES=3000` gave 60,000 cases: 28,691 printed the same, 30,784 rejected by both, 523 LLVM fallbacks, no differences, none only LLVM accepts, and 2 that only we accept (VOP1 SDWA with `clamp` and both modifiers; LLVM's reason is unknown).
- **Every opcode**: `every_opcode_matches_llvm` (ignored by default, about a minute) tries every opcode number of every format in a few plain forms. llvm-mc decodes 1539 opcodes that way, and all 1539 are in our table with the same text. Our table additionally has `v_illegal` (LLVM decodes only the all-zero word) and the VOP3 forms of `v_interp_p1_f32`/`p2_f32`, which the plain forms do not exercise.

Not checked: the 32-wave lane-mask printing beyond what the random tests cover, and anything about what instructions do. llvm-mc only knows syntax.

## Translation to MSL (milestone 2)

`translate::translate(&Request) -> Result<Translated, TranslateError>`.

### Model

A straight register model, not SSA. The "IR" is the decoded instruction list split into basic blocks at branch targets:

- Each Metal thread is one lane. SGPRs, VGPRs, `vcc`, `exec`, `m0` and `scc` are local variables (`uint`, `scc` is `bool`); only the ones the program touches are declared.
- A lane mask (exec, vcc, a VOPC result, a carry out) holds this lane in bit 0 of its low half. VALU compares write 0 or 1; scalar arithmetic on masks is computed exactly on those values. Every vector instruction and export runs under `if (exec_lo & 1u)`; consecutive vector instructions share one such `if` until something other than a guarded statement is emitted or a statement writes `exec` (2026-11-21: one `if` per instruction made Metal's compiler about 20% slower on large programs).
- `s_cbranch_execz`/`execnz`/`vccz`/`vccnz` test bit 0. In vertex and pixel programs they branch per lane, which is right for the usual "skip if no lane is active" use. In compute programs the condition is `simd_any` over the Metal SIMD group (32 threads on Apple GPUs), so a SIMD group branches as one, as a 32-lane slice of the wave would on hardware. That keeps `s_barrier` in control flow that is uniform per SIMD group (an execz skip around the work before a barrier is common), and loops that exit through `execz` still end.
- Cross-lane operations: DPP16 quad permutations that read one lane of the quad (`quad_perm:[k,k,k,k]`, full row and bank masks) become `quad_broadcast` of src0, in any VOP1/VOP2/VOPC instruction. Other DPP forms, `readlane` of another lane, `ds_swizzle`, `ds_permute` and ballots are rejected. `v_readfirstlane` reads this lane.
- SDWA: source selects (bytes and words, with sign extension) apply to the sources. A destination select below the whole dword computes the full result, then merges its low byte or word into the selected field of the old register: zeros elsewhere (`UNUSED_PAD`), the field sign-extended upwards (`UNUSED_SEXT`), or the old bits kept (`UNUSED_PRESERVE`). Minecraft's in-world pixel programs use these (2026-11-20).
- The MSL compiles in safe math mode (2026-11-21): with Metal's default fast math, which assumes no NaN or infinity, a Superliminal program produced NaN pixels ([gpu.md](gpu.md)).
- Without branches the body is straight-line code. Since 2026-11-24 branches become nested `if`s and loops where they nest ([below](#toward-a-compiler-2026-11-24)); otherwise (since 2026-11-21) the basic blocks follow each other in address order, each as `if (pc == L) { ... }`: a branch or the fall-through sets `pc`, and the blocks before the target are skipped. Each loop (a backward branch's target up to the last block that branches back to it) is wrapped in `for (;;) { ... if (pc != L) break; }`, so it runs again only while `pc` is back at its start; a branch out of it, or into the middle of one, works because every block checks `pc`. Loops that overlap without nesting fall back to the old form, `for (;;) switch (pc) { case ... }`, where a branch sets `pc` and continues. Why: Metal's compiler (LLVM inside `MTLCompilerService`) treated the old form as one loop around the whole program; sampling it showed about 37% of a large program's compile time in LICM and ScalarEvolution and 17% in CorrelatedValuePropagation. With loops only where the program has them, Superliminal's largest pixel programs (2,500 instructions, 350 KB of MSL) compile in about 780 ms instead of 1,070 ms. Checked on the GPU by `nested_loops_with_early_exits_run_as_on_hardware` (nested loops, a forward branch inside the inner one and an exit out of it) and the polling test below.
- Scalar loads (`s_load_*`, `s_buffer_load_*`) through a base the source pass traces read constant buffers ([below](#toward-a-compiler-2026-11-24)); other scalar loads and buffer loads read guest memory, through a buffer of all guest memory the host binds. V# fields (base, stride, `num_records`, format and destination swizzle in word 3) are decoded in the shader at run time, because Balatro's vertex programs build their V#s at run time: they load them from a table at a computed offset and rewrite word 3's format bits before `buffer_load_format`.
- Images are Metal textures and samplers. Each distinct T# (with its dimension) and S# gets a slot. Where a descriptor comes from is found by a first translation pass: a forward data-flow pass over the control-flow graph follows user SGPRs through `s_mov_b32`/`s_mov_b64` and `s_load_dword*` with an immediate offset (no `soffset`), so a descriptor may sit in user SGPRs or in memory reached by a chain of such loads (`Source::Memory`). Since 2026-11-21 also: `s_buffer_load_dword*` through a V# found that way, at an immediate offset plus, optionally, a dword shifted left by `s_lshl_b32` (`Source::Buffer`; the dword is a user SGPR or itself a buffer dword found this way, `Source::Scaled`; GTA V picks a sampler by index this way, through VCC, once from a user SGPR and once from an index it loads from a constant buffer), and dwords built from inline constants and literals with `s_mov_b32`/`s_mov_b64`, `s_movk_i32` and `s_bfm_b32` (`Source::Constant`; a 32-bit literal in `s_mov_b64` is taken as zero-extended). VCC is followed too, and forgotten at every vector instruction, since VOPC and carry-out forms write it without naming it. A register whose origin differs between paths into a block, or that anything else wrote, is unknown, and an image instruction using it is rejected.
- Since the GTA V Story Mode work (2026-11-21, night): a dword ORed or ANDed with something in place keeps its origin, and the bits are dropped ([decisions.md](decisions.md)); VCC is forgotten only after instructions that can write it (VOPC without an explicit destination, carry ops, explicit VCC destinations, lane reads into VCC), not after every vector instruction, since GTA V keeps sampler indices in VCC across interpolation and arithmetic. With these, 377 of the 401 programs GTA V runs up to the prologue translate (from 324); the rest are 11 descriptors from places not followed yet, `ds_min_f32`, three ray-tracing programs (`image_bvh_intersect_ray`), `image_sample_d`, `buffer_atomic_swap_x2`, `s_bitreplicate_b64_b32` and one program with a sampler slot above 15.
- Stores and atomics write guest memory through the same buffer, which is then `device uchar*` (`writes_memory`). Buffer stores and atomics use the V#'s base, stride and `num_records` like loads; out-of-range stores are dropped and out-of-range atomics return 0. They also skip the guest range `Win.ro`, the image of a loaded module the window covers (see [gpu.md](gpu.md#the-games-code-overwritten-by-the-culling-queue-2026-11-21-later)).
- Buffer loads and stores of dwords with `glc` are relaxed atomics (2026-11-21; loads in a program that writes no memory are `volatile` instead). Other groups of the same dispatch may be polling or writing that memory: with plain accesses Metal's compiler keeps a load out of a polling loop, and the loop never sees the other group's store. GTA V's culling programs pass partial results from group to group this way (a look-back scan: each group polls the flag of the group before it). Checked on the GPU by `a_group_polling_a_glc_flag_sees_another_group_set_it`: with plain loads the polling group spun until the loop guard stopped it. Relaxed atomics order nothing else; whether the data written before the flag is always seen with it is not checked.
- LDS is `threadgroup uint lds[]` in compute programs, sized from `LDS_SIZE` of `COMPUTE_PGM_RSRC2` in 512-byte units (32 KiB when it is 0, Metal's limit). Out-of-range reads return 0 and writes are dropped. `s_barrier` is `threadgroup_barrier` on threadgroup and device memory.

### Stages

- **Vertex, NGG** (`ngg: true`, Balatro's case: the program in the ES slot runs as the merged ES/GS program): user SGPRs start at s8, `s3` (merged wave info) is set so that the prologue's `s_lshr_b64 exec` arithmetic leaves this lane active, v5 is the vertex index and v8 the instance index (as SharpEmu-mac's `Gen5NggExports.cs` documents them). `s_sendmsg` (GS_ALLOC_REQ) and the primitive export are dropped: one vertex per thread, primitives assembled by Metal, as in the non-culling case. `pos0` becomes `[[position]]`, `paramN` becomes `float4 pN [[user(locnN)]]`.
- **Vertex, legacy VS** (`ngg: false`): user SGPRs from s0, vertex index in v0, instance index in v3. Untested.
- **Pixel**: user SGPRs from s0, the primitive mask in the next SGPR is 0. VGPRs are laid out by `SPI_PS_INPUT_ADDR`. `v_interp_p1`/`p2` become reads of a Metal-interpolated input `a{attr}` with `[[user(locn{OFFSET})]]` (from `SPI_PS_INPUT_CNTL_n`, or `n` if not given). Inputs that share a location read the same vertex export, as on the hardware; MSL allows each location once, so such programs read one `PsInRaw` field and copy it into each input (Isaac's room floor needs this); the interpolation qualifier follows the i/j VGPRs the instruction reads (center, centroid or sample; perspective or linear). `v_interp_mov` gives a `flat` input. `exp mrtN` becomes `float4 cN [[color(N)]]`; compressed exports are unpacked according to `SPI_SHADER_COL_FORMAT` (FP16, UNORM16, SNORM16, UINT16, SINT16). MRTs whose format is UINT16 or SINT16 are `uint4`/`int4` outputs, so they can target Metal integer formats. `exp mrtz` writes depth. A lane whose exec bit is clear at the `done` export, or that reaches `s_endpgm` without exporting, is discarded.
- **Compute** (`gen5_cs`): user SGPRs from s0, then the workgroup ids X, Y, Z and the threadgroup size, each only when `COMPUTE_PGM_RSRC2` enables it (`TGID_X/Y/Z_EN`, bits 7 to 9; `TG_SIZE_EN`, bit 10, given the thread count as SharpEmu-mac does, which is not what hardware puts there). v0, v1 and v2 hold the thread id in the threadgroup, as many components as `TIDIG_COMP_CNT` says. The layout matches what the 11 compute programs Minecraft runs expect and SharpEmu-mac's `DecodeComputeSystemRegisters`. The renderer dispatches threadgroups of `COMPUTE_NUM_THREAD_X/Y/Z` threads, one Metal thread per lane, so a wave64 is two Metal SIMD groups. No other launch parameters are needed.

### Interface for the renderer

```rust
pub struct Request<'a> {
    pub stage: Stage,            // Vertex, Pixel, Compute
    pub code: &'a [u32],         // from the program address; the end is found by decoding
    pub user_sgprs: u32,         // RSRC2.USER_SGPR
    pub ngg: bool,               // vertex stage: merged NGG program
    pub ps_input_ena: u32,
    pub ps_input_addr: u32,
    pub ps_input_cntl: &'a [u32],
    pub col_format: u32,         // SPI_SHADER_COL_FORMAT
    pub compute_rsrc2: u32,      // COMPUTE_PGM_RSRC2
    pub threads: [u32; 3],       // COMPUTE_NUM_THREAD_X/Y/Z
    pub uint_textures: u32,      // texture slots with UINT formats, bit n for slot n
    pub sint_textures: u32,      // texture slots with SINT formats
}
pub struct Translated { msl, entry, resources, vertex_outputs, color_outputs, writes_depth, guest_memory, writes_memory, lds_bytes }
pub enum Resource { Texture { slot, source, kind, access }, Sampler { slot, source }, Constants { slot, base, bytes } }
pub enum Base { Pointer(Source), Buffer(Source) }
pub enum Access { Sample, Write, ReadWrite }
pub enum Source { UserSgpr(u8), Memory { pointer: Box<Source>, offset: u32 } }
```

`Source::Memory` is resolved on the CPU per draw or dispatch: read two dwords at `pointer` (recursively), form a 64-bit address, and read the descriptor `offset` bytes past it.

Bindings in the generated MSL:

| Binding | What |
| --- | --- |
| `constant uint* user [[buffer(0)]]` | All user SGPR values, as dwords, in order |
| `constant ulong& mem_base [[buffer(28)]]` | Guest address of byte 0 of the memory buffer, when `guest_memory` |
| `device const uchar* mem [[buffer(29)]]` | Guest memory, when `guest_memory` (`device uchar*` when `writes_memory`) |
| `constant uint* cbN [[buffer(1 + N)]]` | Guest memory scalar loads read through a traced base (`Resource::Constants`); `device const` in programs that write memory |
| `[[texture(slot)]]` | `texture2d<float>` (or `texture2d_array`, `texture3d`, `texturecube`) per `Resource::Texture`, `<uint>` or `<int>` for the slots `uint_textures`/`sint_textures` name, with `access::write` or `access::read_write` for images the program stores to |
| `[[sampler(slot)]]` | per `Resource::Sampler` |
| `[[vertex_id]]`, `[[instance_id]]` | vertex stage |
| `[[thread_position_in_threadgroup]]`, `[[threadgroup_position_in_grid]]` | compute stage |

The vertex body is also a plain function, `VsOut gen5_vs_body(uint vid, uint iid, constant uint* user, ...)` with the same resource parameters, so the renderer can wrap it (for example for rectangle lists). Entry points are `gen5_vs`, `gen5_ps` and `gen5_cs`.

### Verified

- All 42 Balatro shaders translate, and the MSL compiles with Metal's runtime compiler (`MTLDevice newLibraryWithSource`) in `tests/msl.rs`. The offline compiler (`xcrun metal`) is not installed on vic's machine (Xcode asks for `xcodebuild -downloadComponent MetalToolchain`), so the test uses the runtime compiler instead.
- `tests/unit.rs` translates hand-written programs, assembled with llvm-mc for gfx1013, and compiles each result with Metal: a constant colour and a textured pixel shader; a compute program with workgroup ids, LDS, a barrier, a buffer store and an atomic; descriptors loaded through a pointer table; `image_load`/`image_store`/`image_get_resinfo`; carry arithmetic, DPP quad broadcasts, cube-map ops, `v_med3_i32`, `v_mul_hi_i32`; `image_gather4_lz` on an array; integer colour exports.
- Integer textures: a texture slot named in `uint_textures` or `sint_textures` is declared `<uint>` or `<int>`, its reads and gathers go to VGPRs as raw integers and its stores take them as integers. Slot numbers are the same whatever the masks, so the renderer can translate a program once, read the descriptors, and translate again with the masks. Captures (version 2) record the masks; version 1 files load with none.
- Minecraft: all 49 programs it runs up to its main menu (11 compute, the rest vertex and pixel) translate and compile. `PS5SLOP_SHADER_DUMP=dir` saves each program the renderer translates with its register state (`capture.rs`), and `cargo run -p gfx10 --example captures -- dir [name]` translates and compiles a directory of them offline, or prints one program's disassembly and MSL. The captures are game data and stay outside the repo.

Checked by drawing: Balatro's title screen and Minecraft's main-menu UI (logo, buttons, text) render through it. Not verified: that compute programs compute the right values (nothing checks their output yet). `v_writelane_b32` and `v_readlane_b32` with a constant lane use one variable per (register, lane), since lanes are not modelled; this covers SGPR spills to VGPR lanes (Minecraft's lighting pixel program). Other lane selects read and write the thread's own value. Programs get the user SGPR count from `SPI_SHADER_PGM_RSRC2`'s 5-bit `USER_SGPR` plus `USER_SGPR_MSB` (bit 27, Mesa's `gfx10.json`); without the high bit a program with 32 user SGPRs got 0 and failed to translate (Minecraft's terrain, 57 draws a frame, 2026-11-20). A texture sampled in a format other than the one its render target or storage image was made in gets a Metal view only when Metal allows it (the same bytes per pixel; `RG11B10Float` and `RGB9E5Float` only as 32-bit integers); otherwise the draw goes without it and the renderer reports it. Astro Bot sampled an `RG11B10Float` target as `RGBA16Float`, and the view creation aborted the process (2026-11-20). Pixel inputs read with `v_interp_mov_f32`, or whose `SPI_PS_INPUT_CNTL` has `FLAT_SHADE` (bit 10), are declared `uint4 [[flat]]`, and the vertex function paired with such a pixel program exports those locations as `uint4` (`as_type`), so integer values pass bit for bit (2026-11-20): Minecraft's terrain passes a texture-set index this way, and as float bits it arrived as 0, so every block sampled its whole group of colour, normal and material cells. Known approximations: integer textures (`uint_textures`, `sint_textures`) are sampled with the sampler like float ones, which Metal allows only unfiltered; `image_store` writes 0 to the components `dmask` leaves out; compute SIMD groups (32 lanes) stand in for wave64 when branching; `v_cvt_pkrtz_f16_f32` rounds to nearest instead of toward zero; denormal and NaN handling follows Metal's defaults; `v_mac_f32` and friends may be fused by the Metal compiler; buffer formats cover every GFX10 `BUF_FMT` with 8-, 16- and 32-bit components and `2_10_10_10` (UNORM, SNORM, USCALED, SSCALED, UINT, SINT, FLOAT; numbering from Mesa's `gfx10-rsrc.json`), but not `10_11_11`, `11_11_10` or `10_10_10_2`, which read as 0 (an unknown format reading as 0 made Minecraft's 16-bit bone indices all 0); out-of-range buffer reads return 0 but are only checked against `num_records`.

## Added for Superliminal and Astro Bot (2026-11-20)

Semantics from AMD's RDNA ISA guide (as recalled) and Mesa's opcode table; each has a hand-written test in `tests/unit.rs` that translates it and compiles the MSL with Metal (no oracle checks the values):

- **`buffer_store_format_x/xy/xyz/xyzw`**: the inverse of `buffer_load_format`: the first n data dwords are packed into the format's first n components (UNORM and SNORM rounded and clamped, scaled formats converted to integers, 16-bit floats to half), other components left as they are. Destination selects are not applied to stores (assumed).
- **`s_getpc_b64`**: the guest address of the next instruction. `Request::address` carries the program's address (captures from version 3 on store it; older ones load with 0). Astro Bot's full-screen vertex programs read their corner table from right after their own code this way; the code's extent is a candidate for the memory window already.
- **`v_mad_u64_u32`, `v_mad_i64_i32`, `v_cmp_*_u64/i64`, `s_bfm_b64`, `s_bitset0/1_b32`**; **`s_trap`** is ignored.
- **`d16`** on `image_load`, `image_store` and the sample instructions: two 16-bit values per VGPR, low half first (half floats for float textures).
- **`image_sample*_o`**: the offset dword (6-bit signed texel offsets) shifts the coordinates by offset / size, rather than Metal's constant offsets. 2D and 2D arrays only.
- **Sampler-adjust samples**: MIMG opcodes `0xA0` to `0xBE` (`OPM` set) are not in the public RDNA2 docs and llvm-mc rejects them. SharpEmu-mac describes them as the PS5's `_A` forms of the sample instructions, each `0x80` above its base, with the same operands; only reserved bits of the sampler differ. We decode them as the base instruction. Seen in GTA V's final pixel program; that it draws right (its logo screen does) is the only check.
- **FLAT and GLOBAL loads** (`*_load_ubyte`, `sbyte`, `ushort`, `sshort`, `dword` to `dwordx4`): through the guest memory window, like buffer loads, with the 64-bit VGPR address (or, for GLOBAL with an SADDR, the SGPR pair plus a 32-bit VGPR) plus the offset. No range check beyond the window's start. Stores since 2026-11-22 (below); atomics are not translated.
- **`image_sample_c*`**: the depth reference is compared with the sampled value by `SQ_TEX_DEPTH_COMPARE` (sampler dword 0, bits 12 to 14, Mesa's `S_008F30_DEPTH_COMPARE_FUNC`), giving 1 or 0. The renderer appends dword 0 of each sampler slot's S# after the 32 user SGPRs (`user[32 + slot]`, `binding::SAMPLER_WORDS`). An approximation: one filtered sample compared, not four compared and filtered (no PCF).
- **DPP `quad_perm`** with any permutation (full row and bank masks) in pixel and compute programs: `quad_shuffle` by the thread's `[[thread_index_in_quadgroup]]`.
- **`ds_append`/`ds_consume`** on GDS (`gds` bit) or LDS: an atomic add or subtract of 1 at the base plus `offset`: `M0[31:16]` for the GDS, `M0[15:0]` for LDS. The GDS half is inferred, not from a document: Astro Bot sets M0 to 0x0C600020 and its `DMA_DATA` packets clear and copy the GDS words at 0xC64 to 0xC7C, which only the high half explains (2026-11-21). With the low half, its tile counters were never reset and grew every frame. On hardware a wave adds its active lane count once and every lane gets the old value, then adds its `v_mbcnt` rank; here `v_mbcnt` gives 0 (lanes are threads), so each thread counts itself and gets its own old value. Totals and the indices handed out match; their order does not.
- **`v_cvt_pkrtz_f16_f32`** rounds toward zero (2026-11-21, AMD's ISA guide): a helper `half_rtz` rounds to nearest and steps one unit toward zero when that grew the magnitude, so values past the largest half become 65504 instead of infinity. Checked on the GPU by `packing_halves_rounds_toward_zero`. Superliminal's infinite pixels made a noise square through bloom ([gpu.md](gpu.md)).
- `v_cvt_pknorm_u16_f32` and `_i16_f32` used MSL names that do not exist (`pack_unorm2x16`); now `pack_float_to_unorm2x16` and `pack_float_to_snorm2x16`.

Superliminal: all 16 programs it runs translate.

## Added for Astro Bot (2026-11-21)

Semantics from AMD's RDNA ISA guide (as recalled) unless named otherwise; one test per group in `tests/unit.rs` translates hand-assembled words (llvm-mc, gfx1013), checks the MSL text and compiles it with Metal. No oracle checks the values.

- **Indexed VGPR moves** (`v_movrels_b32`, `v_movreld_b32`, `v_movrelsd_b32`, `v_movrelsd_2_b32`, `v_swaprel_b32`): the register `base + M0` (`movrelsd_2` and `swaprel`: source index `M0[9:0]`, destination `M0[25:16]`). VGPRs are named locals, so an indexed access is a `switch` with one case per VGPR from v0 to the highest the program names; `emit` fills in the cases once the register set is known, and every VGPR in that range is declared. Seven of Astro Bot's pixel programs use these.
- **`s_*_saveexec_b32`** (all ten): the wave32 forms, on `exec_lo`. Astro Bot's ray-traced compute programs are wave32.
- **`v_xad_u32`**: `(a ^ b) + c`.
- **`v_cmp_class_f32`**: a helper `fclass` tests the class mask (signalling NaN, quiet NaN, then negative infinity up to positive infinity, in the guide's order). GTA V's Story Mode needs it too.
- **DPP** beyond full-mask quad permutations, in pixel and compute programs: `row_shl`, `row_shr`, `row_ror`, `row_mirror`, `row_half_mirror`, `row_share`, `row_xmask`, quad permutations with partial row or bank masks, and DPP8. Each is a `simd_shuffle` by the thread's lane in its 32-lane Metal SIMD group (rows of 16 line up with the hardware's); lanes whose source is outside the row, or whose row or bank is masked off, keep their old value unless `bound_ctrl` asks for a 0 source. `fi` is ignored. A wave64 is two SIMD groups here, so nothing crosses lane 31.
- **`v_permlane16_b32`, `v_permlanex16_b32`**: the 4-bit lane selects from the two scalar sources, within the row or from the other row of the 32. `fi` and `bound_ctrl` (op_sel) are ignored.
- **`v_readlane_b32` with a constant lane** that is not an SGPR spill (no `v_writelane` to it before): `simd_broadcast` of lane `k mod 32` in pixel and compute programs. Astro Bot reduces a value over the wave with row shifts, `v_permlanex16` and `v_readlane` of lanes 31 and 63; here the result covers one 32-lane SIMD group.
- **`ds_bpermute_b32`**: `simd_shuffle` by `(addr + offset) / 4` mod 32, in pixel and compute programs. `ds_permute_b32` is not done.
- **`ds_write_addtid_b32`, `ds_read_addtid_b32`** (compute): LDS at `M0[15:0] + offset + 4 * lane`, the lane counted through the threadgroup modulo 64 (wave64 assumed).
- **Image atomics** (`image_atomic_swap`, `cmpswap`, `add`, `sub`, `smin`/`umin`, `smax`/`umax`, `and`, `or`, `xor`; 2D and 2D arrays, one component): Metal texture atomics on a `<uint>` (or `<int>`) `read_write` texture, `Access::Atomic`. The renderer binds an `R32Uint`/`R32Sint` view; 32-bit integer textures are made with `MTLTextureUsageShaderAtomic` (Metal refuses that usage for `R32Float`, so an atomic on a float image does not bind). `glc` returns the old value; `cmpswap` loops on `atomic_compare_exchange_weak`. Astro Bot's pixel program 0x50054fd00 builds per-pixel linked lists with `image_atomic_swap`; a compute program counts into a 2D grid with `image_atomic_add`.
- **Programs that end with a branch back**: `program()` stopped only at `s_endpgm`, so two NGG vertex programs whose last instruction is an `s_branch` back into the body were decoded into their trailer (`sl00`) and rejected as "Invalid(770)". Decoding now also ends at an `s_branch` that no branch jumps past.
- **Pixel inputs that share a location**, where one reader is flat and another is not: copied through `as_type` (the MSL did not compile).
- **Loop guard**: a vertex or pixel invocation gives up after `MAX_BACK_BRANCHES` (1024) backward branches: a pixel is discarded, a vertex returns what it has. A program that never leaves a loop hangs the GPU, and after a hang macOS ignores all of the process's later Metal work. Astro Bot's logo program (0x5009c7000) walks a GPU-built linked list that, with our emulation, sometimes never ends (see [gpu.md](gpu.md#astro-bots-title-2026-11-21)). 1024 is a guess at "more than any honest loop in a vertex or pixel program"; no title seen so far needs more.
- **Compute loop guard (2026-11-21)**: a compute program with a backward branch (`Translated::loop_guard`) gets `device atomic_uint* guard [[buffer(25)]]`, two words the renderer zeroes for each dispatch. A thread gives up after `MAX_COMPUTE_BACK_BRANCHES` (16,384) backward branches of its own, or once all threads of the dispatch together took `GUARD_BUDGET` (2^20) units of 1024: each thread adds a unit every 1024 branches and checks the total at its first backward branch, so a runaway in a grid of millions of threads ends too. Threads that give up count themselves in the second word, which the renderer reports with the program and its user data. In a program with `s_barrier`, a thread that gives up only sets a threadgroup flag; after each barrier every thread reads the flag, waits at a second barrier and leaves if it is set, so the group leaves together; a thread that reaches no barrier within 1024 more branches leaves alone. Before this, compute was not guarded, and GTA V's culling program (see [gpu.md](gpu.md)) kept the GPU busy until the Mac had to be rebooted. Checked on the GPU by `runaway_compute_loops_end_on_their_own` (`crates/gpu/src/metal.rs`): loops that would also stop at a bound from user data (so a guard that failed could not hang the GPU) end after 6 ms in one group, 14 ms in a grid of 2^20 threads (most of them stopped by the budget) and 4 ms in two groups with a barrier, and an honest loop of 4096 turns runs to its end. The limits are guesses. GTA V's programs 0x4242400 and 0x41b3800 gave up in a look-back loop that polled with plain loads (see the `glc` item above).

Of the 138 programs captured from Astro Bot's title level (`captures` example, each compiled with Metal), 116 translated before these changes and 128 after. The other ten:

- **Ray tracing** (8 compute programs, wave32, 16x16 threads): each has three `image_bvh_intersect_ray` instructions. The traversal loop is in the program itself; the instruction tests one BVH node. Translated since 2026-11-21 (below); four of the eight still stop at `s_ff1_i32_b64`. Metal's ray tracing does not fit, since the title builds its BVHs itself in the hardware's format.
- **Two NGG vertex programs** (0x5000f6800 and 0x50011ff00, one hash; 10,000 to 26,000 skipped draws in a three-minute run) that expand items into geometry: lanes vote with `v_mbcnt`, `s_ff1_i32_b64` and `v_bcnt_u32_b32`, compact surviving items into LDS behind an `s_barrier`, each item becomes 10 vertices and 8 triangles, and the program writes its own connectivity with `exp prim` and sizes its output with `GS_ALLOC_REQ`. ## Astro Bot's lighting programs (2026-11-21, later)

Astro Bot lights its G-buffer only in compute programs that also trace rays, so its title logo stayed black until these worked. Checked on the title screen against PS5 captures of it (see [gpu.md](gpu.md#astro-bots-logo-2026-11-21-later)); no unit test checks the results against hardware.

- **`image_bvh_intersect_ray`** (and the `bvh64` form): an MSL helper `bvh_intersect` over guest memory, written from Mesa radv's software emulation of the instruction (`radv_nir_rt_common.c`, MIT; see [references.md](references.md)). The T# base is `(dword0 | dword1[7:0] << 32) << 8`; a node pointer holds the node type in its low 3 bits and the rest is the address in 8-byte units (`(node & ~7) << 3` from the base). Box nodes (type 5, 32-bit bounds; type 4, 16-bit bounds) return the four children the ray enters within `ray_extent`, sorted nearest first when dword 1 bit 31 asks for sorting, `0xFFFFFFFF` for the rest; triangle nodes (types 0 to 3) return `(t, det, i, j)` from the watertight test radv uses, or `(inf, 1, 0, 0)` for a miss; other types return all `0xFFFFFFFF`. The game's descriptor has the same layout as radv's (sorting and "return IJ" set), which is all that was checked; how the hardware treats triangle types 1 to 3 and dword 3 bit 24 clear is assumed.
- **Wave32 lane masks.** A VALU compare, `v_cmpx` or carry-out writes one SGPR in wave32, not a pair. The translator wrote `dst + 1 = 0` always, which in wave32 programs wiped the next register (Astro Bot's lighting programs lost a descriptor that way). A program counts as wave32 when it uses a `*_saveexec_b32` or writes `exec_lo` with a 32-bit scalar instruction.
- **Lockstep wave64 groups.** A compute program whose group is exactly one wave64 (64 threads), that uses LDS and has no `s_barrier`, may pass values between lanes through LDS relying on the wave running in step; Astro Bot's light-culling program reduces each tile's depth range that way. Here such a wave is two Metal SIMD groups, so these programs get a threadgroup barrier before and after every LDS instruction, every conditional branch decided by `wave_any` (a vote of both SIMD groups through threadgroup memory), and a loop guard that makes the whole group leave together (`lockstep_leave`), so no thread waits at a barrier the others skipped. Scalar branches are voted too, which is exact only while scalar values agree across the group. 8 of the title's programs qualify.

Of the 140 programs captured in a 125 s run of the title, 134 translate and compile; the other 6 are the 4 ray-traced programs and the 2 NGG vertex programs that use `s_ff1_i32_b64`.

## Whole-wave lane masks in lockstep programs (2026-11-22)

Outside lockstep programs a lane mask is one bit per thread (bit 0 of the low SGPR), which is exact as long as no lane looks at another lane's bit. Lockstep programs (one wave64 per group, no `s_barrier`) now hold every lane mask as the whole wave's 64-bit value, the same in all 64 threads, as on the hardware (semantics from AMD's RDNA ISA guide, as recalled):

- **Writes from the vector unit** (compares, `v_cmpx`, carries out): a ballot of both SIMD groups through threadgroup memory (`wave_ballot`); inactive lanes give 0. EXEC starts as all 64 lanes.
- **Reads of this lane's bit** (the EXEC guard, `v_cndmask`, carries in, `VCCZ`/`EXECZ`): bit `wl` of the pair, `wl` being `32 * simdgroup + lane in SIMD group`, so it matches the ballot by construction.
- **`v_readlane_b32`** (not a spill) and **`v_readfirstlane_b32`** read the lane from either SIMD group (`wave_readlane`); `readfirstlane` takes the lowest lane in EXEC, lane 0 when EXEC is empty.
- **`v_mbcnt_lo/hi_u32_b32`** count the mask's bits below `wl`; DPP row masks use `wl`'s row.
- Scalar instructions need nothing new: masks are plain 64-bit values, so `s_and_b64 s[0:1], exec, 1`, `s_bcnt1_i32_b64` or `s_cmp_lg_u64 vcc, 0` give what the hardware gives.
- Each exchange uses the other half of a 4-word threadgroup array, so it needs one barrier. Control flow stays the same in both SIMD groups because branches are still voted.

The lockstep set grew too: a one-wave group without `s_barrier` is lockstep when it uses LDS or an instruction that needs whole-wave masks (`crosses_lanes`: a non-spill `v_readlane`, `v_mbcnt`, 64-bit lane counts, `s_cmp_*_u64`, a 64-bit scalar operation that picks lanes out of EXEC or VCC with a constant, a 64-bit vector shift of EXEC or VCC). GTA V's prologue has 20 such programs (8 more than before). Checked on the GPU by `one_wave64_group_sees_whole_wave_masks_and_lanes` (our own program: a lane-0 atomic, lanes 0 and 63 read by all, `v_mbcnt` and a count of a compare mask). Three of GTA V's compute programs (0x4241400, 0x4242400, 0x4244000) stopped tripping the loop guard; whether their results are now right is not checked.

Cost: every mask write in these programs is a barrier. GTA V's prologue went from 1.9 to 1.57 flips a second, because the program that still trips the guard (0x4203300) now pays a barrier per compare on every turn of its runaway loop (1.15 with two barriers per exchange). Why that program loops is not known; see [gpu.md](gpu.md#gta-vs-player-camera-and-compute-programs-2026-11-22).

## Lockstep groups of several waves (2026-11-24)

Outside lockstep programs a wave64 runs as two Metal SIMD groups that know nothing of each other, so an instruction that relies on the 64 lanes running together gets each half's own answer. GTA V's BVH builds sort keys with programs of four waves per group (256 threads, with `s_barrier`) that do exactly that, and the sort came out wrong ([gpu.md](gpu.md#gta-vs-fidelity-frame-time-all-queues-2026-11-24-evening)):

- `0x4245d00`, an exclusive scan of a 256-digit histogram, carries the low half into the high half with `s_bfm_b64 exec, 32, 32` and `v_readlane_b32 s0, v7, 31`. Here EXEC became empty for every thread and `readlane` read lane 31 of the thread's own SIMD group, so the high half lost the low half's total.
- `0x4246c00`, the scatter of each radix pass, ranks equal digits within a wave with `ds_add_rtn_u32` and relies on the hardware applying one wave's LDS atomics in lane order. The two halves interleaved (ranks 0, 32, 1, 33, ...), which made the sort unstable and let padding keys overwrite real ones.

Lockstep now also covers groups of several whole wave64s that use an instruction from `crosses_lanes` or an LDS atomic that returns a value (`ordered_lds`). Each wave works as in a one-wave lockstep program (whole-wave masks, voted branches, exchanges through threadgroup memory), but its two SIMD groups meet by themselves instead of through a group barrier: each publishes how many meetings it has reached in a threadgroup atomic (`lockstep_seq`) and waits for its partner (`wave_meet`), so waves stay independent between `s_barrier`s as on the hardware. A meeting gives up after `MEET_SPINS` polls, so a lost partner slows a dispatch but cannot hang the GPU. A returning LDS atomic runs in the low half, then the high half, between meetings; within one SIMD group Metal was seen to apply same-address atomics in lane order (not documented). 512 bytes of threadgroup memory are kept from the LDS for the exchange slots.

A lockstep group must run whole. Direct dispatches sized in threads (`USE_THREAD_DIMENSIONS`) used to run a partial last group, where a wave can lack its second SIMD group and every meeting waits out its spins; that made GTA V's tree optimisers (`0x41ef400`, `0x41f2700`) take seconds per dispatch and stalled the load. Such dispatches of lockstep programs now run whole groups with grid bounds, as indirect ones do.

Checked: the sort's eight passes in a fresh GTA V load against a CPU oracle (stable counting sort of a dumped input, `PS5SLOP_GPU_WATCH` with a range and `PS5SLOP_GPU_WATCH_DUMP`): every pass a permutation, the result sorted. GPU tests run our own four-wave program (`waves_of_a_bigger_group_keep_their_halves_in_step`, `a_partial_group_of_waves_runs_whole`).

## One lane's EXEC outside lockstep programs (2026-11-22)

Outside lockstep programs a scalar instruction that writes EXEC (`s_wqm_b64`, `s_mov_b64 exec, -1`, `s_and_saveexec_b64`, ...) now keeps only bit 0 of the result and clears `exec_hi`. Before, `s_wqm_b64 exec, exec` turned this lane's 1 into 0xF (the whole quad), and a waterfall loop (`v_readfirstlane`, `v_cmpx`, `s_andn2_b64 s[n], s[n], exec`, `s_cbranch_scc1` back) never ran out of lanes: `v_cmpx` clears only bit 0, so lanes 1 to 3 stayed set in the saved mask. The loop hit its 1024-turn cap and the fragment was discarded. GTA V's forward glass programs (the depot's wire-glass partition, 0x115a7a9a00 and 0x115a7a4c00) run such a loop over their light list, and every pane fragment was dropped. In the single-lane model the quad's other lanes are other threads, so no scalar result can make them this thread's work.

`exp mrtz` now writes depth only when its R component is enabled, and its B component (the sample mask) goes to `[[sample_mask]]`. A GTA V program that exports only the sample mask (`exp mrtz off, off, v9, off`) wrote an unexported register as depth before.

## Toward a compiler (2026-11-24)

The translator emits each instruction as its own MSL snippet, with every rare case written out inline, and leaves the rest to Metal's compiler. That compiler optimises well, but only what it can see, and on a GPU the price of what it cannot remove is higher than on a CPU: registers per thread set how many threads a core holds, spills go to memory, and the instruction cache is small.

**Measured** in GTA V's Fidelity frame with `scripts/shader-profile` ([debugging.md](debugging.md)):

- Compiled programs are 14 to 217 KiB. `0x115b185c00` is 3.7 KB of guest code (about 900 instructions), 140 KB of MSL and 136 KiB of GPU code, and spills 592 bytes per thread. Spills show up in about 200 encoders of the frame.
- In `0x115b185c00` (a lockstep compute program, six dispatches, 9.2 ms), dropping the barriers around LDS operations or making the wave votes local to a SIMD group did not make it faster (the results are wrong; it only measures the ceiling). Dropping the per-dword fallback of multi-dword scalar loads, which almost never runs, made it 7.1 to 7.6 ms. The fallback is now two window lookups instead of one per dword ([gpu.md](gpu.md)).
- A pixel program of the heaviest pass (`0x115aff4800`, 7 of pass 106's 16 draws) starts with 11 scalar loads of constants and descriptors, among them an `s_buffer_load_dwordx16`; each is a per-pixel read of guest memory through the window lookup. Most of its 89 KB of MSL is these loads.

**Plan.** Each step keeps the current form as the fallback for what it cannot handle, so programs never stop translating; old and new output of the same program, compared on the GPU, is the oracle. Each step is measured by code size, spills and time per program in the frame, and the frame must stay pixel-identical.

1. **Constant buffers (done, 2026-11-24).** A scalar load whose base the source pass traces (a pointer at a known place, or a V# at one), with an immediate dword-aligned offset and no `glc`, in a program without `s_dcache_inv`/`s_gl1_inv`, reads `cbN[k]` with a constant index from a buffer the renderer binds per draw (`Resource::Constants`, slots 1 to 16). The renderer resolves the base address the way it resolves texture descriptors and binds the no-copy window over it, the same memory programs use; where the range is not all guest memory it binds a copy made when encoding, with zeros for dwords outside guest memory, as scalar loads read them. Programs that write guest memory declare the buffers `device const`, not `constant`: Metal read a `constant` buffer as it was when the dispatch began, and GTA V's `0x115b233800` reads back with a scalar load what it stored before (a GPU test, `a_scalar_load_sees_what_the_program_stored_before_it`, got 0xA1 for the 0x77 it stored). Loads whose results only image and sampler instructions use (descriptors, which the renderer binds itself) are left out, after a first pass that finds which SGPRs anything else reads. GTA V's Fidelity frame, same pixels, four interleaved rounds, medians of five warm frames: 111 to 93 ms of GPU time (render passes 68.9 to 61.3 ms, compute 42.1 to 31.4 ms; `0x115b241400` 7.5 to 2.8 ms, `0x115b185c00` 7.6 to 5.3 ms, pass 129 5.2 to 2.2 ms), CPU time per frame unchanged at 11.9 ms. The heaviest pass (106) measured 18.7 against 21.2 ms, within its usual spread.
2. **Structured control flow (done, 2026-11-24).** `Nest` in `flow.rs` reads the branches as the guest compiler's structured code: a forward conditional branch skips the region up to its target (`if (!(cond)) { ... }`), and when that region ends with an unconditional branch further on, the code it skips is the else part; a backward branch target starts a loop up to the last branch back to it (`for (;;) { ... break; }`), branches back to the innermost loop's start are `continue` (with the loop guard) and branches to the instruction after it are `break`. Branch conditions are the same as before (votes in lockstep programs, `simd_any` in other compute programs). A program where any branch leaves the region it is in, or jumps back to an outer loop, keeps the `pc` dispatcher; in GTA V's Fidelity frame that is 3 of 281 programs (pixel programs whose uniform branch inside an execz skip jumps past the skip's end). Checked on the GPU by `a_uniform_if_else_runs_one_arm`, `a_branch_out_of_the_region_it_is_in_runs_as_on_hardware` (fails with the region check removed) and the nested-loop test. Same pixels; GPU time 93 to 84.5 ms in four interleaved rounds (render 60.9 to 58.5 ms, compute 31.6 to 26.2 ms; `0x115b27fe00` 5.0 to 1.6 ms, `0x115b241400` 2.8 to 1.7 ms, pass 106 20.4 to 18.3 ms; passes 40 and 208 measured 0.5 and 0.4 ms slower). Compile time was not measured. Still to do: the exec guard inside each `if`, which the compiler may not see through.
3. **Fewer whole-wave masks.** In lockstep programs, find which mask values reach an instruction that needs the whole wave (`crosses_lanes`, execz branches around barriers or LDS) and ballot only those.
4. **Formats known at translation.** Buffer formats and strides from V#s the source pass traces are passed in the request, like integer texture formats, so `buffer_load_format` becomes the one conversion it needs.

An SSA form between decoding and emission is not planned until a step needs it; Metal's compiler builds SSA from the register locals already.

## Open questions

- The renderer asked for buffers at `[[buffer(1 + slot)]]` with their V#s at `[[buffer(30)]]`. Balatro's vertex programs build their V#s at run time, so the translator reads guest memory instead; static buffer slots could come back as an optimisation where a V# provably sits in user SGPRs.
- Not translated yet: ballots, `ds_swizzle`, `ds_permute`, wave operations that cross 32 lanes outside lockstep programs (`ds_bpermute` still works within 32-lane halves), scratch (except unwritten reads, above), GDS ordered counts, 64-bit atomics other than the bitwise ones and `swap_x2` (see GTA V below), and the `a16` form of `image_bvh_intersect_ray`. NGG programs that use LDS and barriers need a mesh-shader path (above).
- How AGC programs reach the GPU: the header's program-address registers are patched by `sceAgcCreateShader`, and the renderer finds the code through `SPI_SHADER_PGM_LO_*`; the `.ags` parsing here is only for tests.
